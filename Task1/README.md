## Задание 1. Анализ безопасности системы (As‑Is)

### 1. Выявление конфиденциальных данных, не учтённых во внутренних системах

На основе описания компании и диаграммы C4 выявлены следующие категории конфиденциальных данных, которые обрабатываются, но не имеют специального учёта, защиты и контроля:

| № | Категория данных | Примеры полей | Где хранятся / обрабатываются | Примечание |
|---|------------------|---------------|-------------------------------|------------|
| 1 | Персональные данные (PII) | ФИО, дата рождения, телефон, email, адрес регистрации, место работы/учёбы | Excel-файлы «Patients», журналы записи, сканы договоров | Нет разграничения доступа, все сотрудники имеют доступ к общей папке |
| 2 | Медицинская тайна | Диагнозы, результаты анализов, история болезней, назначения, заключения | Папки пациентов (Data file), журналы специалистов, реестры лаборатории | Хранятся в открытом виде в Excel/PDF/JPG, без шифрования |
| 3 | Паспортные данные и СНИЛС | Серия, номер паспорта, СНИЛС, полис ОМС/ДМС | Сканы документов в папках пациентов | Не маскируются, доступны всем, кто имеет доступ к папке |
| 4 | Финансовые данные (платежи) | Сумма оплаты, способ оплаты, реквизиты карт (маскировка не применяется), данные о возвратах | 1С:Бухгалтерия, файлы Excel (дублируются), ККМ | Передаются по TCP/IP без TLS, файловый режим 1С не обеспечивает аудит |
| 5 | Данные о сотрудниках (HR) | ФИО, паспортные данные, ИНН, СНИЛС, зарплата, банковские счета | 1С:Бухгалтерия, файлы на общем диске | Доступ у бухгалтеров и администраторов, нет ограничений по принципу минимальной привилегии |
| 6 | Данные о ТМЦ | Номенклатура, количество, цена, поставщики, договоры | 1С:Торговля и склад, Excel-отчёты | Нет интеграции с бухгалтерией на уровне объектов, ручной ввод |
| 7 | Логи доступа и аудит | IP-адреса, время входа, действия пользователей | Active Directory, файловый сервер (журналы событий) | Не централизованы, не анализируются, нет алертов при подозрительной активности |

**Вывод:** все перечисленные данные обрабатываются без должной защиты, не классифицированы, не имеют политик хранения и удаления, а доступ не контролируется на уровне записей.

### 2. Диаграммы потоков данных (DFD) для текущего состояния (As‑Is)

На основе C4-диаграммы и описания бизнес-процессов выделены **5 ключевых процессов**. Для каждого составлена DFD (в текстовом виде, диаграммы будут выполнены в draw.io и загружены в репозиторий).

#### Процесс 1: Запись пациента на приём

- **Источник:** Пациент (личное обращение или звонок) → Сотрудник ресепшен.
- **Действия:** Внесение данных пациента (ФИО, контакты) в Excel-файл «Patients» и в журнал специалиста («Journal-Doctor-FIO»).
- **Хранилища:** Общая папка на файловом сервере (папки «Pacients», «Journals»).
- **Потоки данных:** Ресепшен → Excel-файлы (чтение/запись). Врач → чтение своего журнала.
- **Уязвимости:** Нет аутентификации на уровне файлов, любой сотрудник может редактировать любую запись; данные передаются по сети в открытом виде (SMB без шифрования); нет версионности; журналы не структурированы для автоматизации.

#### Процесс 2: Ведение медицинской карты и анализов

- **Источник:** Врач / Лаборатория.
- **Действия:** Врач вносит диагнозы, назначения, результаты осмотров в файлы пациента (Excel, PDF, JPG). Лаборатория передаёт реестры анализов (Excel) и сканы результатов.
- **Хранилища:** Папки пациентов (Pacient1-FIO-BD), папка Laboratory Registry.
- **Потоки:** Врач ↔ файлы пациента; лаборатория (внешняя система) → реестры Excel (возможно, по электронной почте или через общую папку).
- **Уязвимости:** Данные не шифруются; нет разграничения доступа между врачами (врач видит карты всех пациентов); нет аудита изменений; интеграция с лабораторией не автоматизирована (ручной импорт Excel).

#### Процесс 3: Приём платежей и бухгалтерский учёт

- **Источник:** Пациент → Кассир.
- **Действия:** Кассир принимает оплату через ККМ, информация о платеже передаётся в 1С:Бухгалтерия через OLE по TCP/IP. Кассир также вручную дублирует данные в Excel (для отчётности). Бухгалтер обрабатывает платежи, начисляет зарплату, готовит отчёты.
- **Хранилища:** 1С:Бухгалтерия (файловый режим), Excel-файлы.
- **Потоки:** ККМ → 1С (OLE/TCP/IP); кассир → Excel; бухгалтер → 1С.
- **Уязвимости:** Передача ККМ–1С не шифруется (TCP/IP без TLS); OLE – устаревший и небезопасный протокол; дублирование в Excel приводит к расхождениям; файловый режим 1С не масштабируется и не имеет аудита на уровне записей.

#### Процесс 4: Учёт ТМЦ

- **Источник:** Складской сотрудник.
- **Действия:** Внесение данных о поступлении, перемещении и списании товаров в 1С:Торговля и склад. Данные частично синхронизируются с 1С:Бухгалтерия через OLE.
- **Хранилища:** 1С:Торговля и склад (файловый режим), Excel для дополнительных отчётов.
- **Потоки:** Склад → 1С; 1С Торговля → 1С Бухгалтерия (OLE).
- **Уязвимости:** OLE-соединение небезопасно; отсутствие контроля доступа на уровне объектов; ручной ввод создаёт риск ошибок; нет интеграции с закупками.

#### Процесс 5: Взаимодействие с лабораторией (внешний процесс)

- **Источник:** Лаборатория (внешняя система).
- **Действия:** Предоставление реестров анализов и результатов в виде Excel-файлов, которые сохраняются в папку «Laboratory Registry» на общем диске. Врачи просматривают эти файлы для внесения данных в карты пациентов.
- **Хранилища:** Общая папка.
- **Потоки:** Лаборатория → общая папка (возможно, через FTP или email); врачи → чтение.
- **Уязвимости:** Нет защищённого канала передачи; файлы не зашифрованы; нет контроля целостности; используются устаревшие форматы без версионности.

### 3. Аудит мер безопасности и список проблемных зон

Сопоставление текущего состояния с требованиями 152-ФЗ и архитектурными практиками:

| № | Требование / Практика | Текущее состояние | Проблема |
|---|------------------------|--------------------|-----------|
| 1 | Идентификация и аутентификация | Есть AD, но доступ к данным на файловом сервере открыт для всех доменных пользователей | Отсутствует RBAC на уровне файлов/папок, любой сотрудник может читать/писать все данные |
| 2 | Шифрование данных при передаче | Используется SMB, TCP/IP без TLS, OLE | Данные передаются в открытом виде, перехват возможен внутри сети |
| 3 | Шифрование данных при хранении | Нет | Файлы и базы 1С не зашифрованы; при физическом доступе к серверу данные легко извлечь |
| 4 | Аудит доступа и действий | Отключён или не настроен | Нет возможности определить, кто и когда обращался к медицинским картам |
| 5 | Управление жизненным циклом данных | Нет политик хранения | Данные хранятся бесконечно, нарушается принцип минимизации |
| 6 | Разграничение доступа (ABAC/RBAC) | Отсутствует | Врач видит всех пациентов, бухгалтер имеет доступ к медицинским данным (через общую папку) |
| 7 | Маскирование / обезличивание | Не применяется | В аналитических отчётах используются реальные ФИО, номера телефонов |
| 8 | Реагирование на инциденты | Нет SIEM, алертов | Обнаружение утечек только по жалобам клиентов |
| 9 | Соответствие 152-ФЗ | Частично (1С сертифицирована, но файловый режим не аттестован) | Нарушение требований к защите персональных данных при их обработке в ИСПДн |

**Список проблемных зон (сохранить в отдельный документ):**

1. Общий доступ к файловому хранилищу без контроля прав.
2. Отсутствие шифрования на всех уровнях (покой, передача, резервные копии).
3. Нет аудита и логирования действий с данными.
4. Дублирование данных в Excel и 1С, ведущее к несогласованности.
5. Ручной ввод и отсутствие автоматизации – высокий риск ошибок.
6. Отсутствие классификации данных и тегирования.
7. Нет политик удаления устаревших данных.
8. Небезопасные протоколы интеграции (OLE, TCP/IP без TLS).
9. Отсутствие системы управления ключами шифрования.
10. Нет механизма для реализации права на забвение.
11. Не контролируется доступ к данным со стороны внешних подрядчиков (лаборатория).

### 4. Список данных для защиты и способы защиты

| Категория данных | Примеры полей | Способы защиты |
|------------------|---------------|----------------|
| **PII** | ФИО, дата рождения, телефон, email, адрес | **Шифрование** at‑rest (AES-256), **маскирование** при выводе на экран для ролей, не требующих доступа, **обезличивание** для аналитики (хеширование) |
| **Паспортные данные** | Серия, номер, СНИЛС, полис | **Шифрование**, **маскирование** (показывать только последние 4 цифры), доступ только уполномоченным сотрудникам с MFA |
| **Медицинские данные** | Диагнозы, анализы, история болезни | **Шифрование**, **разграничение доступа** по принципу «лечащий врач», аудит всех обращений |
| **Финансовые данные** | Сумма, способ оплаты, данные карт | **Шифрование** при передаче (TLS), **маскирование** номера карты (показывать звёздочки), хранение в отдельной защищённой БД |
| **Данные о сотрудниках** | Зарплата, банковские счета | **Шифрование**, доступ только у бухгалтера и руководителя, двухфакторная аутентификация |
| **ТМЦ** | Номенклатура, цены, поставщики | **Шифрование** (при передаче), контроль доступа на уровне записей |
| **Логи доступа** | IP, время, пользователь, действие | **Хеширование** для сохранения целостности, защита от удаления, шифрование при хранении |
| **Аналитические данные (обезличенные)** | Агрегированные отчёты без PII | **Обезличивание** (удаление прямых идентификаторов), использование псевдонимов |

### 5. Механизм тегирования данных

Разработана **система тегов** для классификации данных и автоматического применения политик безопасности. Теги присваиваются на уровне:
- **БД (таблицы, столбцы)** – через метаданные (Apache Atlas, OpenMetadata).
- **Файлы (Excel, PDF, JPG)** – через расширенные атрибуты файловой системы или отдельный каталог метаданных.
- **API-контракты** – в OpenAPI-спецификации.

**Набор тегов:**

| Тег | Описание | Применяемые политики |
|-----|----------|----------------------|
| `PII` | Персональные данные (ФИО, телефон, email) | Шифрование, маскирование при выводе, аудит доступа, ограничение на передачу внешним системам |
| `Sensitive` | Особо чувствительные (паспорт, СНИЛС, биометрия) | Строгое шифрование, двухфакторный доступ, запрет на копирование |
| `Medical` | Медицинские данные | Шифрование, доступ только врачам с ролью «лечащий», аудит изменений |
| `Financial` | Платёжные данные | Шифрование, маскирование, отдельное хранилище, соответствие PCI DSS |
| `Internal` | Внутренние служебные данные | Шифрование, доступ ограничен сотрудниками компании |
| `Public` | Публичные данные (например, расписание) | Без ограничений, но с защитой целостности |
| `Retention_1y` / `Retention_5y` / `Retention_10y` | Срок хранения | Автоматическое удаление по истечении срока |
| `AuditRequired` | Требуется аудит каждого обращения | Включение логирования, алерты при аномалиях |

Механизм применения тегов:
1. **Инвентаризация:** все источники данных сканируются, полям/файлам вручную или автоматически (через регулярные выражения) присваиваются теги.
2. **Хранение тегов:** в каталоге данных (Apache Atlas) теги сохраняются как метаданные.
3. **Политики:** на основе тегов строятся политики доступа (ABAC), шифрования, маскирования, удаления.
4. **Проверка в CI/CD:** при релизе автоматически проверяется, что все новые поля/эндпоинты имеют корректные теги, иначе сборка блокируется.

### 6. Список инструментов, способов и мер для обеспечения конфиденциальности

| Область | Инструменты / Способы | Назначение |
|---------|------------------------|------------|
| **Шифрование** | TLS 1.3 (передача), AES-256 (хранение), HashiCorp Vault (управление ключами) | Защита данных в канале и на диске, централизованное управление ключами |
| **Контроль доступа** | IAM (Keycloak / AD), RBAC + ABAC, MFA | Ограничение доступа на основе ролей и атрибутов (тегов) |
| **Маскирование** | Динамическое маскирование на уровне API Gateway или БД (например, Oracle Data Masking, PostgreSQL anonymization extensions) | Сокрытие конфиденциальных полей для неподходящих ролей |
| **Аудит и логирование** | ELK / Loki, SIEM (Wazuh), интеграция с Data Lineage | Централизованный сбор событий, обнаружение аномалий, реагирование |
| **Data Lineage** | Apache Atlas / OpenMetadata | Отслеживание происхождения данных, визуализация потоков, влияние изменений |
| **Тегирование** | Apache Atlas, встроенные теги в S3/MinIO, OpenAPI-расширения | Классификация данных, автоприменение политик |
| **Управление жизненным циклом** | Политики удаления в БД и S3, скрипты очистки по тегам | Автоматическое удаление по истечении срока хранения |
| **Обфускация / Обезличивание** | Хеширование (SHA-256 с солью), генерация псевдонимов | Подготовка данных для аналитики и ML без PII |
| **Защита от утечек (DLP)** | Мониторинг исходящего трафика, запрет на скачивание больших массивов | Предотвращение эксфильтрации |
| **Безопасная интеграция** | API-контракты с маскировкой, использование шифрованных очередей (Kafka SSL) | Защита данных при обмене между системами |
| **Обучение персонала** | Регулярные тренинги по безопасности, политике обработки PII | Снижение человеческого фактора |

### 7. Доработанные диаграммы (с добавленными мерами)

На каждой DFD необходимо добавить элементы защиты. Ниже приведено описание дополнений для каждого процесса (визуально на диаграммах будут отображены иконки замков, тегов, журналов аудита).

**Процесс 1 (Запись пациента):**
- Входной поток от пациента к ресепшен – защищён через TLS (если через портал), но пока офлайн, добавить шифрование при передаче данных в БД (переход на клиент-серверное приложение вместо Excel).
- Хранилище данных пациента – шифрование at‑rest, тегирование PII, аудит всех записей/изменений.
- Доступ врачей – RBAC, только к своим пациентам.
- Добавлен компонент «Data Lineage» для отслеживания создания и изменений записи.
![Диаграмма с исправлениями](Процесс 1 (Запись пациента).drawio.png)
[Ссылка на исходный код UML](Процесс 1 (Запись пациента).xml)

**Процесс 2 (Медицинская карта):**
- Все файлы пациентов шифруются (S3 с SSE-KMS).
- Теги Medical, Sensitive – применяется политика: доступ только лечащему врачу, все обращения логируются.
- Внедрена система контроля версий файлов (например, с хешами).
- Передача от лаборатории теперь по защищённому API (HTTPS, OAuth2), данные автоматически загружаются в озеро данных, где маскируются для неавторизованных.
![Диаграмма с исправлениями](Процесс 2 (Медицинская карта).drawio.png)
[Ссылка на исходный код UML](Процесс 2 (Медицинская карта).xml)

**Процесс 3 (Платежи):**
- ККМ ↔ 1С: переход на защищённый канал (TLS) и использование REST API вместо OLE.
- Данные платежей хранятся в отдельной БД с шифрованием, тег Financial, маскирование номера карты.
- Бухгалтер получает доступ через двухфакторную аутентификацию, все операции логируются.
- Excel-дублирование исключено, переход на единую систему учёта.

[Ссылка на исходный код UML](Процесс 3 (Платежи).xml)


**Процесс 4 (ТМЦ):**
- Замена файлового режима 1С на клиент-серверный, интеграция через защищённый API.
- Тегирование данных о ТМЦ (Internal), контроль доступа по ролям (склад, бухгалтер).
- Аудит изменений номенклатуры и цен.
![Диаграмма с исправлениями](Процесс 4 (ТМЦ).drawio.png)
[Ссылка на исходный код UML](Процесс 4 (ТМЦ).xml)

**Процесс 5 (Лаборатория):**
- Вместо обмена Excel-файлами – защищённый API (REST с JWT), передача только минимально необходимых данных (минимизация).
- Полученные результаты сразу шифруются и тегируются (Medical, Sensitive).
- Доступ к результатам – только через API с проверкой ролей и атрибутов.

На всех диаграммах добавлены:
- **Компонент «Policy Enforcement Point»** – применяет политики доступа на основе тегов.
- **Компонент «Audit Log»** – записывает все действия.
- **Компонент «Data Masking»** – маскирует поля перед выводом.
