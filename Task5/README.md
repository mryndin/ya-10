
## Разработка cutover‑плана миграции

### 1. Выбор стратегии миграции

#### 1.1. Доступные варианты

| Стратегия | Описание | Преимущества | Недостатки |
|-----------|----------|--------------|------------|
| **High‑level design (Big Bang)** | Полная остановка старой системы и единовременный переход на новую | Быстрый переход, минимальное время параллельной работы | Максимальный риск; любой сбой парализует бизнес; требует длительной подготовки |
| **Parallel run** | Старая и новая системы работают одновременно, нагрузка распределяется постепенно | Безопасность; возможность сравнения результатов; лёгкий откат | Высокие затраты на синхронизацию данных; сложность поддержки двух систем; длительный период |
| **Branch by abstraction** | Постепенное вырезание функциональных модулей из монолита с заменой на микросервисы через фасад/абстракцию | Минимальный простой; инкрементальный подход; снижение рисков; возможность обучения команды поэтапно | Требует грамотного архитектурного проектирования; сложность управления зависимостями; длительная миграция |

#### 1.2. Обоснование выбора: **Branch by abstraction (Strangler Fig pattern)**

**Почему этот подход оптимален для «Медикаменте»:**

1. **Критичность бизнеса** – медицинские услуги не терпят длительных простоев. Внезапный сбой при Big Bang поставит под угрозу здоровье пациентов и репутацию компании.
2. **Сложность данных** – данные разбросаны по Excel, 1С и файловой системе. Нет единой модели. Постепенная миграция позволяет очищать и трансформировать данные по частям.
3. **Ограниченность ресурсов** – текущий IT-штат (3 человека) не способен обеспечить полную параллельную работу. Branch by abstraction позволяет нанимать специалистов поэтапно и распределять нагрузку.
4. **Соответствие 152‑ФЗ** – поэтапное внедрение шифрования и аудита даёт возможность на каждом шаге проверять соответствие требованиям без риска всеобщей утечки.
5. **Возможность обучения** – команда постепенно осваивает микросервисы, Kubernetes, новые технологии, а не «падает в омут с головой».

**Ключевые принципы выбранной стратегии:**

- Строим **API‑фасад (API Gateway)** перед существующими системами (1С, файловое хранилище, Excel).
- Постепенно **вырезаем функциональные модули** (пациенты, записи, медкарты, платежи, ТМЦ, лаборатория) и заменяем их микросервисами.
- Используем **Feature Toggles** – часть пользователей работает через старую систему, часть – через новую.
- Данные **синхронизируем** через событийную шину (Kafka) между старой и новой системами, пока идёт миграция.
- Завершаем **отключением старой системы** после полной замены всех модулей и успешного параллельного тестирования.

### 2. Cutover‑план (поэтапный)

План разбит на **6 основных этапов**, каждый с подзадачами, сроками, ответственными и мерами по снижению рисков.

| № | Этап | Описание действия | Ключевые задачи | Ответственные | Время/Сроки | Риски и меры по снижению |
|---|------|-------------------|-----------------|---------------|-------------|--------------------------|
| **0** | **Подготовка и анализ** | – Инвентаризация всех данных и процессов.<br>– Документирование бизнес-логики (Excel‑макросы, ручные операции).<br>– Создание карты данных (Data Flow Mapping).<br>– Классификация PII и медицинской тайны.<br>– Разработка целевой архитектуры (C4).<br>– Выбор инструментов (Kafka, K8s, API Gateway).<br>– Найм дополнительных специалистов (DevOps, Java‑разработчики, DBA). | 1. Провести интервью с бизнес‑владельцами.<br>2. Составить реестр данных и полей.<br>3. Определить «золотой источник» для каждой сущности.<br>4. Подготовить контракты API для новых микросервисов.<br>5. Настроить базовую инфраструктуру (Kubernetes, сеть, VPN). | Технический директор, Бизнес‑аналитик, Администратор сети | 4 недели | – Задержка найма → начать с аутсорсингом.<br>– Неполная документация → привлечь ключевых пользователей.<br>– Изменение требований → внедрить гибкую методологию. |
| **1** | **Создание фасада (API Gateway) и абстракций** | – Развёртывание API Gateway (Kong / Spring Cloud Gateway).<br>– Реализация прокси‑слоя для всех существующих интерфейсов (1С, файловая система).<br>– Внедрение аутентификации/авторизации (JWT, интеграция с AD).<br>– Настройка маршрутизации запросов на старую систему через фасад. | 1. Развернуть Kong.<br>2. Написать адаптеры для вызова 1С через OLE (временно) и REST.<br>3. Настроить TLS и базовое шифрование.<br>4. Создать централизованный аудит всех запросов через фасад.<br>5. Реализовать Feature Toggle – переключение запросов на новые сервисы. | DevOps-инженер, Java‑разработчик, Администратор | 3 недели | – Сложность адаптации 1С → использовать COM-обёртки.<br>– Производительность фасада → нагрузочное тестирование.<br>– Некорректная маршрутизация → детальное логирование и мониторинг. |
| **2** | **Поэтапная замена модулей (Strangler)** | – Замена модуля «Пациенты»: новый микросервис PatientService, БД PostgreSQL.<br>– Замена модуля «Записи к врачу».<br>– Замена модуля «Медицинские карты» (переход на S3).<br>– Каждый модуль проходит тестирование в параллельном режиме с эталонной старой системой. | 1. Разработать микросервис с API, тегами, маскированием.<br>2. Написать ETL для переноса исторических данных.<br>3. Настроить синхронизацию изменений через Kafka между старой и новой БД (пока идёт миграция).<br>4. Включить Feature Toggle для 10% «пилотных» пользователей.<br>5. Сравнить результаты работы старой и новой системы.<br>6. Постепенно увеличивать процент трафика на новый сервис. | Tech Lead, разработчики (2 чел.), DBA, аналитик | 12 недель (по 3 недели на модуль) | – Ошибки в логике → проводить регрессионное тестирование каждого модуля.<br>– Расхождение данных → разработать механизм реконсиляции.<br>– Затягивание сроков → использовать MVP-подход, отложить некритичный функционал. |
| **3** | **Миграция данных и интеграции** | – Переход на клиент-серверную 1С (замена файлового режима).<br>– Замена OLE-интеграции ККМ на REST API.<br>– Настройка защищённого API с лабораторией (вместо Excel).<br>– Перенос всех файлов (PDF, JPG) в S3 с шифрованием.<br>– Внедрение Data Lake (обезличенные данные) и витрин. | 1. Перевести 1С на MS SQL Server.<br>2. Разработать API‑контракты для ККМ и лаборатории.<br>3. Написать миграционные скрипты для данных.<br>4. Настроить DLP и аудит доступа. | DBA, разработчики интеграций, администратор 1С | 8 недель (параллельно с этапом 2) | – Ошибки в данных при миграции → делать бэкапы и чек-суммы.<br>– Сбои при переходе на клиент-сервер 1С → тестирование на стенде.<br>– Лаборатория не готова к API → предусмотреть адаптер для временного файлового обмена. |
| **4** | **Финальное тестирование и параллельный прогон** | – Полное функциональное тестирование всех модулей новой системы.<br>– Нагрузочное тестирование для проверки масштабируемости.<br>– Запуск параллельной работы всей старой и новой системы на 2‑4 недели.<br>– Обучение сотрудников работе в новой системе.<br>– Проверка соответствия 152‑ФЗ (аудит, шифрование, согласия). | 1. Провести UAT (User Acceptance Testing) с ключевыми пользователями.<br>2. Запустить мониторинг производительности и ошибок.<br>3. Сравнить бизнес‑результаты (отчёты, финансы) – допустимое расхождение <0.1%.<br>4. Обучить всех сотрудников (ресепшен, врачи, кассиры, бухгалтеры, склад).<br>5. Провести внутренний аудит безопасности. | Технический директор, бизнес‑аналитик, QA‑инженер, HR-менеджер | 4 недели | – Пользователи не принимают систему → усилить обучение, сделать «горячую линию».<br>– Производительность не соответствует → оптимизировать запросы, увеличить ресурсы.<br>– Нарушения безопасности → доработать политики доступа. |
| **5** | **Окончательный переход (Cutover)** | – Отключение старой системы (файловый сервер, OLE, старые интеграции).<br>– Перенаправление всех пользователей на новую платформу.<br>– Перевод DNS, замена сертификатов.<br>– Запуск финального мониторинга и режима 24/7. | 1. В ночь перехода остановить старую систему.<br>2. Проверить целостность данных в новой системе.<br>3. Переключить маршрутизацию на API Gateway.<br>4. Включить все автоматические оповещения.<br>5. Объявить «ледниковый период» – никаких изменений на 2 недели. | DevOps, администратор, техдиректор | 1 день (выходной / ночь) | – Непредвиденный сбой при отключении → план отката (см. ниже).<br>– Потеря данных → иметь финальный бэкап старой системы. |
| **6** | **Пост‑миграционное наблюдение** | – Интенсивный мониторинг в течение месяца после перехода.<br>– Сбор обратной связи, исправление мелких дефектов.<br>– Оптимизация производительности.<br>– Передача знаний команде поддержки.<br>– Выключение старого оборудования. | 1. Ежедневные отчёты об ошибках и производительности.<br>2. Оперативное реагирование на инциденты.<br>3. Проведение пост‑мортем (post‑mortem) через месяц.<br>4. Демонтаж старого сервера (архивация данных). | Команда поддержки (2 чел.), DevOps, техдиректор | 4 недели | – Скрытые дефекты → иметь усиленную команду поддержки.<br>– Рост нагрузки выше ожидаемого → автоскейлинг в K8s.<br>– Усталость команды → чередовать смены, мотивация. |

### 3. Управление рисками и план отката (Rollback)

#### 3.1. Ключевые риски и контрмеры

| Риск | Вероятность | Влияние | Меры предотвращения | План действий при наступлении |
|------|-------------|---------|----------------------|--------------------------------|
| **Сбой при отключении старой системы** | Средняя | Критическое | – Тщательное тестирование.<br>– Полный бэкап перед cutover.<br>– Включить мониторинг критических путей. | – Немедленное переключение DNS обратно на старую систему (в течение 15 мин).<br>– Информирование пользователей о технических работах.<br>– Детальный анализ причин. |
| **Ошибки в бизнес-логике** | Высокая | Высокое | – Автоматическое сравнение результатов старой и новой систем в параллельном режиме.<br>– Тщательный UAT. | – Откат изменённых микросервисов до предыдущей версии.<br>– Использование Feature Toggle для возврата на старую логику для отдельных функций. |
| **Некорректная миграция данных** | Средняя | Критическое | – Проверка контрольных сумм.<br>– Поэтапный перенос с валидацией.<br>– Резервные копии. | – Восстановление данных из бэкапа.<br>– Ручная корректировка (при участии бизнес-аналитика).<br>– Повторная миграция с исправленными скриптами. |
| **Низкая производительность новой системы** | Средняя | Высокое | – Нагрузочное тестирование.<br>– Автомасштабирование в Kubernetes.<br>– Оптимизация запросов. | – Увеличение ресурсов (CPU/память).<br>– Включение кэширования.<br>– Временный перевод части нагрузки на старую систему. |
| **Неготовность пользователей** | Высокая | Среднее | – Обучение заранее.<br>– Создание инструкций и чат-бота.<br>– Пилотное внедрение на группе. | – Проведение дополнительного обучения.<br>– Горячая линия поддержки в первый месяц.<br>– Отсрочка отключения старого интерфейса для некоторых пользователей. |
| **Нарушение 152‑ФЗ** | Низкая | Критическое | – Внедрение шифрования и аудита с первого этапа.<br>– Юридическая экспертиза.<br>– Проведение DPIA. | – Приостановка обработки данных до устранения нарушений.<br>– Уведомление Роскомнадзора (при необходимости). |

#### 3.2. Роли и ответственность

| Роль | Ответственность |
|------|------------------|
| **Технический директор** | Общее руководство миграцией, принятие решений о cutover, утверждение планов, связь с бизнес-руководством. |
| **Ведущий архитектор** | Проектирование абстракций, контроль качества кода, ревью микросервисов, управление API Gateway. |
| **DevOps‑инженер** | Развёртывание инфраструктуры (K8s, Kafka, мониторинг), CI/CD, управление релизами, настройка резервирования. |
| **DBA (администратор БД)** | Миграция данных, переход 1С на клиент-сервер, обеспечение целостности и производительности БД. |
| **Разработчики (2-3 чел.)** | Реализация микросервисов, написание адаптеров, тестирование, исправление дефектов. |
| **Бизнес-аналитик** | Анализ требований, валидация бизнес-логики, тестирование пользовательских сценариев, обучение пользователей. |
| **Администратор сети** | Настройка сетевого оборудования, DNS, сертификатов, обеспечение безопасности каналов. |
| **Менеджер по качеству (QA)** | Разработка тест-планов, проведение функционального и нагрузочного тестирования, проверка соответствия. |
| **Руководители отделов (ресепшен, врачи, бухгалтерия, склад)** | Организация обратной связи от пользователей, участие в UAT, поддержка при внедрении. |
| **Юрист / DPO** | Проверка соответствия 152‑ФЗ, разработка политик согласий и хранения, контроль аудита. |

### 4. План отката (пошаговый)

Если критический сбой происходит в течение первых 48 часов после переключения:

1. **Остановить новые микросервисы** (scale down до 0).
2. **Переключить маршрутизацию API Gateway обратно на старые прокси** (которые ведут к старой системе – 1С и файловый сервер).
3. **Восстановить репликацию данных из бэкапа** (если данные в новой БД были повреждены).
4. **Уведомить всех пользователей** о временном возврате к старой системе (по email, SMS, через внутренний портал).
5. **Начать детальный анализ** логов и метрик для выявления причины.
6. **После устранения причины** повторить cutover в согласованное время (при выходе на плановое окно).

Для всех этапов миграции заранее создаются **checklist-ы** и **runbook-и**, которые проверяются на тестовом стенде.

### 5. Заключение

Выбранная стратегия **Branch by abstraction** позволяет минимизировать бизнес-риски, обеспечивая постепенное, контролируемое внедрение новой архитектуры. Cutover-план разбит на логические этапы с чёткими сроками и ответственными. План отката и меры по снижению рисков делают переход управляемым и безопасным. Документ может служить основой для утверждения руководством и для выполнения технической командой.
