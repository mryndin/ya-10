
## Оценка Data Encryption at Rest and In Transit

### 1. Классификация данных и обоснование необходимости защиты

В компании «Медикаменте» обрабатываются различные категории данных, требующие защиты в соответствии с Федеральным законом № 152-ФЗ «О персональных данных», медицинской тайной (ст. 13 Федерального закона № 323-ФЗ), а также внутренними политиками безопасности.

| № | Категория данных | Примеры полей | Необходимость защиты | Риски при отсутствии защиты |
|---|------------------|---------------|----------------------|----------------------------|
| 1 | **Персональные данные (PII)** | ФИО, дата рождения, телефон, email, адрес, паспортные данные, СНИЛС, полис ОМС/ДМС | Обязательное требование 152-ФЗ; идентификация личности; высокая чувствительность | Штрафы до 75 млн руб. (ст. 13.11 КоАП РФ); потеря доверия клиентов; уголовная ответственность |
| 2 | **Медицинские данные (медицинская тайна)** | Диагнозы, результаты анализов, история болезни, назначения, заключения врачей | Требование законодательства о врачебной тайне; высокая репутационная значимость | Утечка может нанести вред здоровью/репутации пациентов; судебные иски; потеря лицензии |
| 3 | **Финансовые данные** | Суммы платежей, способы оплаты, номера банковских карт (маскированные), данные о зарплатах сотрудников, банковские счета | Защита от мошенничества; соответствие 152-ФЗ и требованиям платёжных систем (PCI DSS) | Финансовые потери; кража средств; штрафы регуляторов |
| 4 | **Данные о ТМЦ и закупках** | Номенклатура, цены, поставщики, договоры, складские остатки | Коммерческая тайна; защита от недобросовестной конкуренции | Потеря конкурентных преимуществ; утечка ценовой политики |
| 5 | **Логи доступа и аудит** | IP-адреса, время входа, действия пользователей, запросы к данным | Необходимость для расследования инцидентов; соответствие требованиям аудита | Невозможность выявления нарушений; отсутствие доказательной базы при проверках |
| 6 | **Конфигурационные данные и ключи шифрования** | Пароли, сертификаты, ключи AES, токены доступа к API | Критически важно для работы всех механизмов защиты | Компрометация ключей ведёт к полной потере контроля над защитой данных |
| 7 | **Аналитические данные (обезличенные)** | Агрегированные отчёты, статистика, дашборды | Обезличенные данные менее чувствительны, но требуют защиты от реидентификации | Деанонимизация может раскрыть PII, что приведёт к тем же рискам |

### 2. Инструменты защиты данных (шифрование at‑rest и in‑transit)

Для каждой категории данных предлагаются следующие инструменты и методы защиты. Реализация должна быть единообразной на всей платформе.

| Категория данных | Шифрование при передаче (In‑Transit) | Шифрование при хранении (At‑Rest) | Дополнительные инструменты (маскирование, контроль доступа, аудит) |
|------------------|---------------------------------------|-----------------------------------|----------------------------------------------------------------------|
| **PII** | TLS 1.3 для всех внешних и внутренних соединений; VPN для межсервисного обмена (при необходимости) | AES-256 для БД (PostgreSQL с TDE или pgcrypto), SSE-KMS для S3/объектного хранилища | Динамическое маскирование на уровне API Gateway (показ только последних 4 цифр); ABAC на основе тегов; Audit Log всех операций чтения/записи |
| **Медицинские данные** | TLS 1.3; защищённые очереди (Kafka с TLS и SASL) | AES-256; отдельные ключи для каждого пациента (или для группы); шифрование файлов (PDF, JPG) с использованием S3 SSE‑KMS | Маскирование при выводе для ролей, не связанных с лечением; строгое ABAC (только лечащий врач); версионирование и хеширование для контроля целостности |
| **Финансовые данные** | TLS 1.3; защищённые REST API; использование токенизации для номеров карт при передаче | Шифрование колонок в БД с использованием pgcrypto; отдельное хранилище для токенов; шифрование at‑rest на уровне диска | Маскирование номеров карт (показывать только ****); двухфакторная аутентификация для бухгалтеров; строгий аудит всех платёжных операций |
| **Данные о ТМЦ** | TLS 1.3 для API 1С и внутренних сервисов | Шифрование БД 1С (при переходе на клиент-сервер) и файлов с прайс-листами | Ролевой доступ (склад/бухгалтер); маскирование цен для отдельных ролей; аудит изменений номенклатуры |
| **Логи и аудит** | Передача логов по защищённому каналу (TLS syslog) | Хранение в WORM-хранилище с шифрованием at‑rest; защита от удаления | Неизменяемость логов; индексация для быстрого поиска; интеграция с SIEM |
| **Ключи шифрования** | Передача ключей только через защищённый канал (TLS) с взаимной аутентификацией | Хранение в аппаратном модуле безопасности (HSM) или в HashiCorp Vault с шифрованием master‑ключа | Ротация ключей по расписанию; строгий доступ (только уполномоченные администраторы); аудит всех операций с ключами |
| **Аналитические данные (обезличенные)** | TLS 1.3 для доступа к витринам данных | Шифрование at‑rest в озере данных и витринах | Обезличивание PII (псевдонимы, хеши) при загрузке; K‑анонимизация для агрегатов; доступ через API с проверкой прав |

### 3. Автоматизированный контроль защиты данных

Для непрерывного мониторинга и быстрого реагирования на инциденты предлагается внедрить следующие средства автоматизированного контроля:

| Средство контроля | Назначение | Инструменты |
|-------------------|------------|-------------|
| **Система обнаружения аномалий** | Выявление нетипичных паттернов доступа к данным (например, массовое скачивание PII, доступ в нерабочее время) | SIEM (Wazuh / Splunk) + ML-модели; интеграция с Audit Log |
| **Мониторинг целостности данных** | Контроль изменений в критических таблицах и файлах; обнаружение несанкционированных модификаций | Tripwire / AIDE; контроль хешей на S3 |
| **Сканирование уязвимостей** | Периодическое сканирование инфраструктуры и кода на наличие уязвимостей, влияющих на защиту данных | Nessus / OpenVAS; SAST/DAST в CI/CD (SonarQube, OWASP ZAP) |
| **Управление политиками безопасности** | Автоматическое применение политик шифрования, маскирования, доступа на основе тегов; проверка соответствия | Apache Atlas / OpenMetadata (политики на основе тегов); Open Policy Agent (OPA) для микросервисов |
| **Аудит доступа и оповещения** | Централизованный сбор логов, корреляция событий, отправка алертов DPO и администраторам | ELK / Loki + AlertManager; интеграция с почтой и мессенджерами |
| **Управление ключами и сертификатами** | Автоматическая ротация ключей, проверка срока действия сертификатов, генерация новых ключей | HashiCorp Vault с Auto‑Unseal; AWS KMS / GCP KMS с автоматической ротацией |
| **Проверка соответствия в CI/CD** | Автоматическая проверка наличия тегов, шифрования, ограничений доступа в новых релизах | Плагины в Jenkins / GitLab CI; статический анализ манифестов Kubernetes (OPA) |
| **DLP (Data Loss Prevention)** | Контроль исходящего трафика и действий пользователей для предотвращения эксфильтрации данных | DLP-агенты на рабочих станциях; мониторинг загрузок и отправок по email |

### 4. Реестр программных и аппаратных средств защиты данных

В таблице приведён перечень необходимых средств с указанием назначения и места развёртывания.

| № | Наименование средства | Тип | Назначение | Место развёртывания | Примечание |
|---|------------------------|-----|------------|---------------------|------------|
| 1 | **HashiCorp Vault** | Программное | Централизованное управление ключами шифрования, токенами, сертификатами; ротация ключей | Кластер Kubernetes (on‑premise или облако) | С поддержкой Auto‑Unseal через облачный KMS или HSM |
| 2 | **HSM (аппаратный модуль безопасности)** | Аппаратное (или облачный HSM) | Безопасное хранение master‑ключа; генерация ключей | В дата-центре или облачный сервис (например, Yandex Cloud HSM) | Обязателен для соответствия высоким требованиям (например, для ключей шифрования ПДн) |
| 3 | **AWS S3 SSE‑KMS / Yandex Object Storage KMS** | Облачное / программное | Шифрование объектов в озере данных и файловых хранилищах | В облачной платформе | Использовать собственные ключи (CMK) или управляемые провайдером |
| 4 | **PostgreSQL с TDE / pgcrypto** | Программное (БД) | Шифрование данных на уровне таблиц/колонок; прозрачное шифрование на диске | Внутренний кластер БД | TDE требует Enterprise-версии; pgcrypto доступен в Open Source |
| 5 | **OpenSSL / Let's Encrypt** | Программное | Генерация и управление TLS‑сертификатами для внутренних и внешних сервисов | Интегрировано в CI/CD и Ingress-контроллеры | Автоматическое обновление сертификатов |
| 6 | **Wazuh / TheHive** | Программное (SIEM + SOAR) | Сбор логов, корреляция событий, обнаружение аномалий, оповещения | Выделенный сервер или облачная инсталляция | Интеграция с Audit Log и Kafka |
| 7 | **Apache Atlas + OpenMetadata** | Программное | Каталог данных, тегирование, применение политик безопасности на основе тегов | Кластер на Kubernetes | Интеграция с Hive, HDFS, Kafka для Data Lineage |
| 8 | **Open Policy Agent (OPA)** | Программное | Унифицированное управление политиками доступа (ABAC) для микросервисов и API Gateway | Sidecar‑контейнеры в Kubernetes | Политики пишутся на Rego и применяются ко всем запросам |
| 9 | **Kong / Spring Cloud Gateway с плагинами** | Программное (API Gateway) | Терминация TLS, аутентификация, динамическое маскирование данных на выходе | Пограничный слой инфраструктуры | Плагины для маскирования и валидации JWT |
| 10 | **Elasticsearch / Loki + Grafana** | Программное | Централизованное хранение и визуализация логов; создание дашбордов для аудита | Кластер на Kubernetes | Использовать для быстрого поиска по логам и алертинга |
| 11 | **SonarQube / OWASP ZAP** | Программное (SAST/DAST) | Автоматический поиск уязвимостей в коде и API на этапе CI/CD | Встроено в пайплайн разработки | Проверка на наличие insecure direct object references, слабое шифрование |
| 12 | **Tripwire / AIDE** | Программное | Контроль целостности системных файлов и конфигураций | На серверах приложений и БД | Обнаружение несанкционированных изменений |
| 13 | **DLP‑агенты (например, InfoWatch / Symantec DLP)** | Программное + агенты на ПК | Контроль действий сотрудников с конфиденциальными данными; блокировка несанкционированной передачи | Рабочие станции + сетевые шлюзы | Особенно важно для ресепшена, бухгалтеров, врачей |
| 14 | **Мониторинг сетевого трафика (TLS-инспекция)** | Аппаратное / программное (например, Zscaler) | Просмотр зашифрованного трафика для выявления утечек (с соблюдением законности) | На границе корпоративной сети | Требует правового обоснования и согласия сотрудников |
| 15 | **Система резервного копирования с шифрованием** | Программное (например, Veeam с шифрованием) | Шифрованное хранение бэкапов at‑rest и передача по TLS | Интегрируется с хранилищами | Ключи для бэкапов также должны управляться через Vault |

### 5. Заключение

Предложенная стратегия охватывает все состояния данных (at‑rest и in‑transit), учитывает требования российского законодательства, а также типовые риски для медицинской организации. Классификация данных позволяет применить дифференцированные меры защиты, а автоматизированный контроль обеспечивает непрерывное соблюдение политик и быстрое реагирование на инциденты. Реестр программных и аппаратных средств даёт чёткое понимание необходимых инвестиций и этапов внедрения.
